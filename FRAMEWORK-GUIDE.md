# 🧩 White-Label PWA Framework — Onboarding Guide

This is the Dala Dala Water app, refactored into a reusable framework.
One codebase, deployed separately per client. New client = clone → edit
one file → run one command → push. No other code changes needed for a
typical water/gas/shop-style ordering app.

---

## What changed from the original app

Nothing changed in *behaviour* — Dala Dala Water works exactly as before.
What changed is that **every business-specific detail moved into
`js/config.js`**: colors, wording, product catalog, contact info,
delivery areas, PWA metadata. The page files (`home.js`, `about.js`,
etc.), styles, and service worker are now 100% generic and shouldn't
need touching for a new client.

Two files are now *generated*, not edited by hand:
- `index.html` — generated from `index.template.html` + config
- `manifest.json` — generated fully from config

A new `build.js` script does that generation.

---

## Onboarding a new client (e.g. a gas refill business)

1. **Clone this template** into a new folder / new GitHub repo
   (same as Part 1, Step 1 in `DEPLOY.md` — just use the template
   instead of the old Dala Dala zip).

2. **Edit `js/config.js` only.** Change:
   - `businessName`, `shortName`, `tagline`, `heroSubtitle`, `emoji`
   - `phone`, `whatsappNumber`
   - `theme` — pick colors for the new brand (these are applied live
     as CSS variables, no CSS editing needed)
   - `home`, `order`, `about`, `contact`, `delivery`, `map` — all the
     page wording
   - `deliveryAreas` and `products` — the actual catalog. The product
     schema (`size`, `pack`, `price`, `image`, `description`) is
     generic enough to hold "13kg Cylinder" / "Refill" just as well as
     "500ml" / "1×12 Carton" — no schema changes needed for gas,
     groceries, or most small-catalog shops.
   - `meta` — SEO description, theme color, category tags

3. **Drop the client's product photos** into `/images`, matching the
   filenames referenced in `config.js`.

4. **Run the build script** from the project folder:
   ```
   node build.js
   ```
   This regenerates `index.html` and `manifest.json` to match the new
   config. Requires Node 18+ (already on your machine).

5. **Commit and push**, then deploy to Vercel exactly as in `DEPLOY.md`
   Part 1 (new GitHub repo → new Vercel project → live URL).

6. If they also want a Play Store APK, follow `DEPLOY.md` Part 2,
   pointing the TWA manifest at the new Vercel URL.

That's the whole onboarding flow — one file edited by hand
(`config.js`), one command run, one push.

## What you get for free by keeping it templated

- **Consistent quality bar.** Every client gets the same tested PWA
  shell, offline support, and WhatsApp order flow — bugs fixed once
  in the template benefit every future client (though already-deployed
  clients need the fix re-applied and re-pushed individually, since
  each is a separate deployment).
- **Fast turnaround.** A new client should be a same-day deploy:
  mostly filling in `config.js` and taking product photos.
- **No cross-tenant risk.** Each client is a fully separate deployment
  (separate repo, separate Vercel project) — no shared database, no
  chance of one client's data or config ever touching another's. This
  matches how the app works today (WhatsApp-based ordering, no backend).

## When you'd outgrow this template model

This clone-per-client approach is right for what this app is today —
a catalog + WhatsApp order form with no login, no backend, no
per-client data storage. If a future client needs things like: order
history / a customer dashboard, staff logins, real-time stock, or
in-app payment tracking, that's a different shape of product (more
like Merkaz POS or GO OS) — worth a separate conversation rather than
stretching this template to fit.

## File reference

| File | Edit per client? |
|---|---|
| `js/config.js` | ✅ Yes — the only file you should need to touch |
| `build.js` | ❌ No — generic build script |
| `index.template.html` | ❌ No — generic template |
| `index.html` | ❌ No — generated by `build.js`, don't hand-edit |
| `manifest.json` | ❌ No — generated by `build.js`, don't hand-edit |
| `css/styles.css` | ❌ No — colors come from `config.js` theme at runtime |
| `js/app.js`, `router.js`, `sw.js`, `js/pages/*`, `js/components/*` | ❌ No — fully generic |
| `/images` | ✅ Yes — swap in the client's product photos + logo/icons |
| `/server` | ✅ Yes — deploy one per tenant, only `.env` differs. See `MPESA-SETUP.md` |

## M-Pesa payments

STK Push (Daraja) is supported and off by default per tenant. See
`MPESA-SETUP.md` for the full setup — deploying the server, wiring
Daraja credentials, and flipping `payments.mpesaEnabled` in
`config.js`.
